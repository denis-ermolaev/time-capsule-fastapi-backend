## 1. Концепция: зачем унифицировать коммиты

Хорошая история коммитов решает три задачи:

1. **Автоматическая генерация changelog'а** — из коммитов можно собрать `CHANGELOG.md`
2. **Определение следующей версии** — `fix:` → patch, `feat:` → minor, `BREAKING CHANGE:` → major
3. **Быстрая навигация** — `git log --oneline --grep="^feat"` показывает только новые фичи

Без стандарта:

```
f4a3c21 asd
b2d1e34 фикс
9c8b712 апдейт
a1b2345 хз что
```

Со стандартом:

```
f4a3c21 feat: добавить эндпоинт создания капсулы
b2d1e34 fix: обрабатывать отрицательные даты в unlock_at
9c8b712 docs: добавить пример API в README
a1b2345 test: добавить параметризованные тесты для Capsule
```

## 2. Структура коммита

```
<type>(<scope>): <subject>      ← заголовок (max 72 символа)
                                 ← пустая строка (обязательно)
<body>                           ← тело (опционально, на русском)
                                 ← пустая строка (обязательно, если есть footer)
<footer>                         ← footer (опционально)
```

**Визуально:**

```
┌ type ┐┌── scope ──┐  ┌────── subject ───────────────────────┐
│
    feat           (capsule):                добавить эндпоинт создания с валидацией
│
└─────────────── max 72 символа ────────────────────────┘
```

### Принцип: тип на английском, описание на русском

Вся техническая часть (тип, scope, директивы) — **на английском**.
Содержательная часть (что сделано, почему) — **на русском**.

```
✅ feat: добавить эндпоинт создания капсулы
❌ feat: add capsule creation endpoint             (проект русскоязычный)
❌ фича: добавить эндпоинт создания капсулы       (тип должен быть английским)

✅ fix(auth): обрабатывать просроченный JWT-токен
❌ fix(auth): handle expired JWT token            (описание должно быть на русском)
```

## 3. Типы коммитов (Conventional Commits)

| Тип                 | Когда использовать                                                                                                  | Влияние на версию |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------- |
| **`feat`**     | ✨ Новая функциональность                                                                                       | minor                            |
| **`fix`**      | 🐛 Исправление бага                                                                                                   | patch                            |
| **`refactor`** | ♻️ Переписывание кода без изменения поведения                                                | —                               |
| **`test`**     | ✅ Добавление или правка тестов                                                                             | —                               |
| **`docs`**     | 📝 Документация: README, докстринги, комментарии                                                    | —                               |
| **`style`**    | 🎨 Форматирование: ruff, пробелы, запятые                                                                | —                               |
| **`perf`**     | ⚡ Оптимизация производительности                                                                       | —                               |
| **`build`**    | 📦 Зависимости и сборка: pyproject.toml, uv.lock                                                                   | —                               |
| **`ci`**       | 👷 CI/CD и инфраструктура: GitHub Actions, Dockerfile, Makefile, docker-compose                                       | —                               |
| **`chore`**    | 🔧 Всё остальное обслуживание: зависимости, конфиги, pre-commit, .gitignore, .dockerignore | —                               |
| **`revert`**   | ⏪ Откат коммита                                                                                                         | —                               |

### Быстрое правило выбора типа

Задай себе три вопроса по порядку:

1. **Изменяет логику приложения?** → `feat` / `fix` / `refactor` / `perf`
2. **Это тесты или документация?** → `test` / `docs`
3. **Всё остальное (обслуживание)?** → `build` / `ci` / `chore` / `style` / `revert`

Подробное описание каждого типа — в таблице §3 выше.

## 4. Заголовок (subject)

### Правила

| Правило                                            | Обязательно | Пояснение                                                                                                            |
| --------------------------------------------------------- | ---------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| **Максимум 72 символа**              | ✅                     | Иначе git обрезает в`git log --oneline`                                                                       |
| **Тип — английский**                  | ✅                     | `feat:`, `fix:`, `refactor:`                                                                                            |
| **Описание — русский**              | ✅                     | Понятно всей команде                                                                                        |
| **Повелительное наклонение** | ✅                     | «Добавить», «Исправить», «Переименовать» — не «Добавил», «Исправил» |
| **Без точки в конце**                 | ✅                     | Заголовок — не предложение                                                                             |
| **Нижний регистр после `:`**    | ✅                     | `feat: добавить` — не `feat: Добавить`                                                                 |

### Как формулировать

```
✅ feat: добавить эндпоинт создания капсулы
❌ feat: добавил эндпоинт создания капсулы    (прошедшее время)
❌ feat: добавить эндпоинт создания капсулы.  (точка в конце)
❌ feat: Добавить эндпоинт создания капсулы   (заглавная буква после двоеточия)
❌ feat: добавить эндпоинт создания капсулы для бэкенда капсул времени (> 72 символов)
```

### Scope (область) — когда нужен

Scope — это **модуль/компонент**, который изменяется.

```
feat(capsule): добавить эндпоинт создания
fix(auth): обрабатывать просроченный токен
refactor(security): вынести хеширование пароля
docs(README): добавить инструкцию по установке
chore(deps): обновить fastapi до 0.138.2
```

**Правила scope:**

- Нижний регистр, английский язык
- Одно слово (если нужно — дефис: `ci-cd`)
- Не указывай, если изменение затрагивает несколько областей
- Общие scope для проекта: `deps`, `config`, `ci`, `docker`

**Когда scope НЕ нужен:**

- Изменение глобальное (стиль, CI, зависимости)
- Изменение затрагивает 3+ модуля

```
✅ style: применить форматирование ruff
✅ chore: обновить все зависимости
```

## 5. Тело (body)

### Когда писать тело

Тело нужно, если заголовок не может уместить всю информацию:

- **Почему** сделано именно так (не «что», а «зачем»)
- **Как** это работает (если неочевидно из кода)
- **Какие альтернативы** рассматривались

### Когда тело НЕ нужно

```
✅ feat: добавить health endpoint

   Заголовок говорит сам за себя → тело не нужно.
```

### Структура тела

```
feat(capsule): добавить эндпоинт создания с валидацией

Реализует POST /capsules/:
- Pydantic-модель Item со strict mode
- structlog для логирования запросов
- HTTP 201 при успешном создании

В следующем PR будет добавлена async-сессия.
```

**Правила:**

- Пустая строка после заголовка (обязательно)
- Максимум 72 символа на строку
- Русский язык
- Отвечай на вопрос **«почему?»**, а не «что?»

## 6. Нижний колонтитул (footer)

### Референт задачи

```
feat(capsule): добавить эндпоинт создания

Closes #42
Refs #41
```

```
Implements TASK-123
Related to TASK-120
```

### BREAKING CHANGE

Если изменение ломает обратную совместимость:

```
refactor(capsule): переименовать unlock_at в available_from

BREAKING CHANGE: unlock_at переименован в available_from.
Старые клиенты будут получать 422.
Миграция: заменить unlock_at на available_from во всех запросах.
```

`BREAKING CHANGE:` в footer автоматически делает следующую версию **major**.

### Co-authored-by

Если коммит совместный:

```
feat(capsule): добавить возможность шаринга

Co-authored-by: Иван Иванов <ivan@example.com>
```

## 7. Когда и как коммитить

### Размер коммита

| Правило                                                                     | Комментарий                                      |
| ---------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| **Один коммит = одно логическое изменение** | Не мешай`feat` + `fix` + `style`               |
| **Коммитить часто**                                            | Каждые 15-30 минут работы                  |
| **Не коммитить сломанный код**                        | Тесты должны проходить (кроме WIP) |

### Модель ветвления

```
main
├── feature/add-capsule
├── fix/handle-empty-name
├── refactor/extract-validator
└── docs/update-readme
```

- `feature/<описание>` — новая функциональность (английский)
- `fix/<описание>` — исправление бага (английский)
- `refactor/<описание>` — рефакторинг (английский)
- `docs/<описание>` — документация (английский)
- `chore/<описание>` — обслуживание (английский)

### Интерактивный rebase (объединение коммитов)

Перед отправкой в `main` — объедини черновые коммиты:

```bash
# Объединить последние 3 коммита
git rebase -i HEAD~3

# Из них:
pick f4a3c21 wip: начал делать эндпоинт
pick b2d1e34 правка опечатки
pick 9c8b712 feat: добавить эндпоинт создания капсулы
```

Превращаем в:

```
feat: добавить эндпоинт создания капсулы
```

commands в rebase:

- `pick` — оставить как есть
- `squash` — объединить с предыдущим, объединить сообщения
- `fixup` — объединить с предыдущим, **отбросить** сообщение
- `reword` — изменить сообщение
- `drop` — удалить коммит

## 8. Инструменты для соблюдения стандарта

### gitlint — проверка коммитов

```bash
uv tool install gitlint
gitlint
```

По умолчанию gitlint требует английский. Для русских описаний — ослабить правило `body-first-line`:

```bash
gitlint --ignore=body-first-line
```

Или в `.gitlint`:

```ini
[general]
ignore=body-first-line
```

### commitizen — интерактивное создание

```bash
uv tool install commitizen
cz commit
```

Задаёт вопросы и формирует корректный коммит:

```
? Select the type of change: feat
? What is the scope: capsule
? Write a short description: добавить эндпоинт создания
? Provide a longer description: (enter to skip)
? Are there any breaking changes: No
```

### pre-commit hook (проверка перед push)

В `.pre-commit-config.yaml`:

```yaml
- repo: https://github.com/jorisroovers/gitlint
  rev: v0.19.1
  hooks:
    - id: gitlint
      stages: [commit-msg]
      args: ["--ignore=body-first-line"]
```

### Автоматическое создание CHANGELOG

```bash
uv tool install conventional-changelog-cli
conventional-changelog -p angular -i CHANGELOG.md -s
```

Собирает все коммиты в файл:

```markdown
## 0.2.0 (2026-07-01)

### Features
- capsule: добавить эндпоинт создания (abc1234)
- auth: добавить валидацию JWT-токена (def5678)

### Bug Fixes
- items: обрабатывать пустое имя (ghi9012)
```

## 9. Примеры: хорошо и плохо

### ✅ Хорошо

```
feat(capsule): добавить эндпоинт создания с Pydantic-валидацией

Реализует POST /capsules/:
- Модель Item со strict mode
- Логирование запросов через structlog
- HTTP 201 при успешном создании

Closes #42
```

```
fix(auth): корректно обрабатывать просроченный JWT-токен

Возвращает 401 с понятным сообщением вместо 500.
Добавлен тест для сценария с истёкшим токеном.

Refs TASK-123
```

```
docs(README): добавить инструкцию по установке и запуску

Включает:
- Системные требования (Python 3.14, uv)
- Переменные окружения
- Команды docker compose
- Ссылку на документацию API
```

```
refactor(security): вынести хеширование пароля в отдельный модуль

Переносит bcrypt-логику из auth.py в security/hasher.py.
Подготовка к добавлению Argon2.
```

```
chore(deps): обновить fastapi с 0.108.0 до 0.138.2

Список изменений: https://github.com/fastapi/fastapi/releases/tag/0.138.2
```

```
ci: добавить GitHub Actions для линтера и тестов

Запускает ruff check, ty check и pytest на каждый push.
Требуется uv 0.11+.
```

### ❌ Плохо

```
asd
```

Ничего не говорит. Непонятно, что менялось.

```
fix
```

Нет описания. Непонятно, что и где чинили.

```
FEAT: добавить новую фичу
```

Тип должен быть нижним регистром.

```
feat: добавить новую фичу и пофиксить баг и обновить доки
```

Три изменения в одном коммите. Должно быть три отдельных.

```
feat: added new feature
```

Английский в описании — а должен быть русский.

```
chore: обновить зависимости и починить тесты и добавить логирование и отформатировать код
```

Всё в одном коммите. Нарушение SRP для коммитов.

```
feat: Добавить эндпоинт
```

Заглавная буква после `:`. Должен быть нижний регистр.
